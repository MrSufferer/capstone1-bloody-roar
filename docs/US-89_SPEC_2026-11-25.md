# US-89 Spec: Quick scan for chat files at upload complete

## Status

Ready for implementation. Grilled 2026-11-25 (all recommendations accepted).

## Covers

- Jira US-89 ([BE] C-1), parent EP-3 Chat and messaging.
- NFR-01 (no secrets in the AI corpus), FR-05 (private Issue chat).

## Problem Statement

Chat between a Client and a Developer is private per Issue, and it is the evidence the Arbiter Safe reads in a Dispute. Right now any allowed file type up to 50 MB becomes `ATTACHED` as soon as the upload completes. That means:

- An SVG, HTML or JS file, or an `.exe` renamed to `.png`, can reach the counterparty and the Arbiter.
- A pasted `.env` or private key in a text file stays in chat. A leaked key can drain the wallet that funds or receives USDC escrow.
- Chat files feed the AI corpus, so a secret in a file breaks NFR-01.

## Solution

Applies to `purpose: "CHAT"` only. Other purposes are unchanged.

Checks run in this order and stop at the first failure:

| # | Check | Where | Code |
|---|-------|-------|------|
| 1 | MIME type is in `CHAT_FILE_TYPES` | presign (400) and complete (422) | `FILE_TYPE_NOT_ALLOWED` |
| 2 | Size ≤ 10 MB | presign (400) and complete (422) | `FILE_TOO_LARGE` |
| 3 | Magic bytes match the declared image/PDF type. Text types must be valid UTF-8 with no NUL byte | complete | `FILE_CONTENT_MISMATCH` |
| 4 | Text content has no secret-class match from `scanAndMask` | complete | `FILE_CONTAINS_SECRET` |
| 5 | File name has no secret-class match from `scanAndMask` | complete | `FILE_CONTAINS_SECRET` |

- `CHAT_FILE_TYPES` (in `packages/shared`): JPEG, PNG, GIF, WebP, PDF, text/plain, markdown, diff, patch, JSON. Not allowed: SVG, HTML, JS/TS/CSS, zip, tar, gzip.
- Pass: status `ATTACHED`, same as today.
- Fail: set status `REJECTED`, delete the stored object, keep the row, return 422 `{ error, code }`.
- The 422 names the kind of secret (for example `evm-private-key`) and never the value.

## Decisions

1. Reject only on secret-class matches (keys, JWTs, database URLs and similar). Email and phone matches don't reject.
2. Type and size are checked at presign to fail early, and again at complete because the client can lie.
3. Detection is server-side from bytes only. No fallback on file extension.
4. A secret in the file name rejects with `FILE_CONTAINS_SECRET`.
5. Keep the `REJECTED` row and delete the object. No cleanup job.
6. CHAT only.
7. Error messages never echo the secret.
8. The signature table is hand-written. No new dependency.

## Slices (one PR each, test-first)

- **B1:** add `REJECTED` to `AttachmentStatus`. The migration only runs `ALTER TYPE ... ADD VALUE`, because Postgres can't use a new enum value inside the same transaction. Apply it to the local `_test` DB only, then run `bun run db:generate`.
- **B2:** `CHAT_FILE_TYPES` and a 10 MB cap, enforced at presign and complete.
- **B3:** magic-byte table plus the UTF-8/NUL check, returning `FILE_CONTENT_MISMATCH`.
- **B4:** secret scan on content and file name, returning `FILE_CONTAINS_SECRET`.

## Checks

- One test per error code, run against the `bloody_roar_test` DB with no mocks.
- An `.exe` renamed to `.png` is rejected with `FILE_CONTENT_MISMATCH`.
- A rejected upload leaves a `REJECTED` row and no stored object, and a FILE message can't reference it.
- A valid chat file still becomes `ATTACHED`, and non-CHAT purposes are unchanged.
- A 10 MB text file scans in under 1 second.
- `bun run typecheck` and `bun run lint` pass.
